## 1 Controllerの検索メソッド

[基本版EmployeeController](../EIMS_SpringBoot_Basic/src/main/java/jp/co/trainocate/eims/controller/EmployeeController.java) の48〜75行、[追加版EmployeeController](../EIMS_SpringBoot_Additional/src/main/java/jp/co/trainocate/eims/controller/EmployeeController.java) の69〜96行は、次の3URLを一つの `search` に割り当てています。

- `/selectByEmpNo`：社員番号検索
- `/selectByEmpName`：社員名検索
- `/selectByDeptNo`：部署検索

実際にはURLではなく、`empNo` → 空白以外の `keyword` → `deptNo` の優先順で処理が選ばれます。コード上は `/selectByEmpName?empNo=10001` でも社員番号検索になり、複数条件を送ると社員番号が優先されます。

画面は既に3つの独立フォームです。一方、[共通仕様](../EIMS_Comprehensive_Exercise_Guide.md) の9.2節・9.6節・10.1節も統合 `search` を定義しています（1337、1532、1660〜1662行）。したがって「解答が仕様に違反していた」という評価は適切ではありません。

修正するならControllerを3メソッドに分け、各URLが自分の検索条件だけを扱う形にするのが簡潔です。Serviceの検索メソッドは既に分離されているため、新たなService分割やクラス追加は不要です。

合わせて更新する箇所は、クラス図、URL一覧、シーケンス図、テストです。確認条件は「各URLが該当する検索だけを呼ぶ」「空入力で別の検索に流れない」「通常検索・0件時の遷移が変わらない」です。

## 2 検索の文字数と数値範囲

[共通仕様](../EIMS_Comprehensive_Exercise_Guide.md) 5.5節の937〜948行は、登録・変更時の入力チェックを定めています。検索キーワードの上限や社員番号の入力範囲は明記されていません。

現行の検索Controllerにはキーワードの長さ制限がなく、検索画面にも `maxlength` はありません。社員番号は `Integer` と数値入力を使いますが、業務上の桁数・正数範囲を検証する処理はありません。

[DB定義](../DBSET/EIMS_DBSET/createDB.sql) の氏・名はそれぞれ `VARCHAR(10)` です。ただし、**DBに保存する文字数と検索キーワードの上限は別の仕様**です。初期データが5桁だから社員番号を5桁と決める、という推測もできません。

仕様として少なくとも次を決める必要があります。

| 入力 | 決める内容 |
| --- | --- |
| 社員番号 | 必須、許可する数値範囲、不正な数値形式への対応 |
| 社員名 | 必須、空白のみの扱い、最大文字数、前後空白を除去するか |
| 部署 | 未選択の扱い。存在しない部署番号の直接送信は現行のテスト対象外 |

共通仕様364〜366行では、プルダウンの値域外・改ざん送信などをテスト対象外としています。存在しない部署番号の処理を必須にする場合は、仕様の追記だけでなく学習範囲の変更になります。

修正前の検証では「10文字以内」も候補に挙げましたが、今回の修正ではユーザー指定により「検索の文字数上限なし」を採用しました。DBに保存できる文字数を検索入力の上限として流用しません。

今回の修正ではサーバー側で未入力・空白のみを判定し、長い検索文字列（11文字・256文字）も上限エラーにせず検索へ渡すことを確認します。

## 3 個別クラス図のEntityフィールド

[共通仕様](../EIMS_Comprehensive_Exercise_Guide.md) の9.1〜9.5節では `Employee`・`Department` が型名と `Entity` 表示だけになっています。例として9.2節の1370〜1371行に属性がありません。9.6節の全体図にはJava属性が載っています（1604〜1620行）。配布PDFも同様です。

関連だけを示す図で属性を省略すること自体は誤りではありません。ただし、受講者が担当機能の図だけを見て実装する教材では、Java側の名前を判断しにくくなるため追記は妥当です。

修正案は、各個別図のEntityに実装で使う属性名と型を載せ、全体図・実Entityと照合することです。図が過密になる場合はEntity定義を共通化して各図に参照先を明記する方法もありますが、今回の「個別にも書く」という要望には各図への追記が直接対応します。全図で同じ属性の名前・型が一致することを確認します。

## 5 未入力チェックと共通メッセージ

「nullチェックの指示が全くなかった」「解答にnull判定がない」という評価は、現在の版には当てはまりません。

- 共通仕様126行は、社員番号未入力・社員名nullまたは空文字・部署未選択なら検索せず検索画面を再表示すると明記しています。
- Controllerも `empNo != null`、`keyword != null && !keyword.isBlank()`、`deptNo != null` で分岐しています。
- 有効な条件がなければ部署一覧をModelに設定して `search` を返します。
- 条件なしのControllerテストもあります。ただしメッセージの確認はありません。

不足しているのは、**入力できていない理由を利用者に伝える仕様と実装**です。現行の未入力経路ではメッセージをModelへ格納していません。共通メッセージ一覧2080〜2104行にも検索未入力用の文言はありません。`E001` は検索を実行して0件だった場合の文言なので、未入力とは区別します。

共通仕様1.1.4節には入力チェックを省略できる簡略版もあります（150〜158行）。標準実装・簡略実装・解答例のどこでメッセージを必須にするかを明確にし、評価基準を揃える必要があります。

修正する場合は、検索ごとの未入力判定で `model.addAttribute("message", ...)` を行い、部署一覧を再設定して検索画面を返す方式で対応できます。検索画面にも `message` の表示箇所が必要です。

文言候補は「社員番号を入力してください。」「社員名を入力してください。」「部署を選択してください。」です。まだ採用していない案なので、IDも含めて仕様確定時に共通メッセージ一覧へ追加します。

`null`、空文字、空白のみ、検索結果0件は別々に確認します。3メソッドへ分ける場合は、現行の「条件なしは社員番号で代表する」というテスト方針（共通仕様2071行）も見直し、各検索の未入力とメッセージを個別に確認する必要があります。

## 6 退職者一覧から詳細へのリンク

[退職者一覧](../EIMS_SpringBoot_Additional/src/main/resources/templates/retiree_list.html) 31行の氏名は `span` で、詳細リンクがありません。通常一覧・検索結果は在籍者を対象としており、社員番号検索でも退職者を除外します。

一方、追加版Controllerの `/detail/{empNo}`（100行以降）は退職者も取得でき、[詳細画面](../EIMS_SpringBoot_Additional/src/main/resources/templates/employee_detail.html) 47行には退職状態の表示があります。したがって「表示そのものが不可能」ではなく、**「通常の画面操作で退職者の詳細へ到達できない」**のが問題です。

氏名を既存の `/detail/{empNo}` へリンクさせる最小修正が妥当です。[追加機能設計書](../追加機能の設計書/追加機能設計書.md) の退職者一覧の氏名欄・処理仕様・完了条件・テスト観点も合わせて更新します（434、485、532、546行付近）。

現行表示は「退職状態：退職／在籍」であり、ご指摘の「退職状況：退職中」とは異なります。文言まで変えるかは別に決めます。詳細画面の戻り先は現在一律 `/search` なので、退職者詳細から退職者一覧へ戻すかも仕様で決めると自然です。

修正の確認条件は、退職者一覧の氏名をクリックして対象者の詳細が開き、「退職」が表示されることです。退職者の変更可否やサーバー側の権限制御は、このリンク不足とは別の設計事項です。

## 7 ログイン画面の会員登録

[追加機能設計書](../追加機能の設計書/追加機能設計書.md) は94〜96行で、会員登録ボタンから既存の社員登録画面へ遷移し、未ログインでも登録できる簡略仕様を明示しています。605行の権限表もこれに対応します。[ログイン画面](../EIMS_SpringBoot_Additional/src/main/resources/templates/login.html) 33〜36行はこの仕様に沿っています。

そのため、現行仕様に対する実装ミスではありません。ただし、社員情報管理システムで「会員登録」という名称や自由な自己登録が不自然だという業務上の指摘は妥当です。

| 選択肢 | 変更内容 |
| --- | --- |
| 名称を直す | 「会員登録」を「社員登録」に変える。未ログイン登録の仕様は残る |
| ログイン画面の導線をなくす | ボタンと関連する画面仕様・画面遷移・テストを修正する |
| 社員登録を人事部管理者だけに限定する | 上記に加え、トップ・共通メニューの導線、権限表、登録関連URLのアクセス制御も修正する |

業務モデルに合わせるなら、少なくともログイン画面の自己登録導線を見直す方向を推奨します。ただし、**ボタンを消すだけでは未ログイン登録は禁止されません**。トップ画面・共通レイアウトにも登録リンクがあり、登録Controllerにはその権限確認がありません。

現行教材はURL・HTTPリクエストの遮断を発展オプションとして扱っています（追加仕様105、567、698行付近）。人事部管理者限定のアクセス制御を必須にするかは、教材の学習範囲と合わせて決める必要があります。

## 修正前に揃えること

1. 標準実装の検索入力ルール・メッセージ・長さ上限を決める。
2. 会員登録の修正を名称・画面導線・権限のどこまで行うか決める。
3. 仕様本文、クラス図、URL一覧、解答、テスト、画面画像を同じ内容にする。
4. 採用するPDFとZIPを再生成して配布版へ反映する。

個別の指摘以上に、編集元と配布物の版を揃えることが重要です。テスト解答ZIPは展開済みコードとパッケージ名から異なり、追加機能ZIPは配布版と別アーカイブが混在しています。詳細はREADMEの版の対応表を参照してください。
