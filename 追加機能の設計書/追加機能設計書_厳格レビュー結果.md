> **この文書は2026年7月10日の修正前状態を記録した履歴である。**<br>

## 1. 結論

**初回判定: 要修正（修正前時点の判定）**

設計書の5機能は、画面・Entity・Repository・Service・Controllerへ概ね実装されている。しかし、権限制御の中核であるサーバー側チェックが実装されておらず、設計書の完了条件を満たしていない。加えて、登録時とログイン時のパスワード桁数が矛盾している。

| レビュー観点 | 判定 | 要点 |
| --- | --- | --- |
| 1. `addition` のソースコードへの反映 | **一部未達** | 5機能の主要部は存在するが、Controller側の認証・権限確認が欠落している |
| 2. 矛盾の有無 | **矛盾あり** | 権限制御、一般ユーザーの登録・本人編集、パスワード桁数、退職状態の表記に不一致がある |
| 3. 初心者向けの難易度 | **一部要改善** | 基本構成は共通機能に沿うが、長いRepositoryメソッド名、複雑なThymeleaf条件、表示側だけの権限制御は理解しづらい |
| 4. 誤字 | **明確な重大誤字なし** | 画像参照切れはない。ただし用語の揺れと曖昧な表現がある |
| 5. スクリーンショットと実画面 | **一部不一致** | 多くは実画面由来だが、2枚はDOM加工画像、複数枚は一時的なDB状態を前提とする |

## 3. 最優先で直すべき問題

### [重大] R-01 サーバー側の認証・権限制御が実装されていない

設計書は次を完了条件・テスト観点としている。

- 4.8 完了条件: 「一般ユーザーが管理操作を直接実行できないようにする」
- 4.9 テスト観点: 「URL直接入力で不正操作できない」
- 4.4 画面例: 全社員一覧を管理者限定にする場合はController側でも権限を確認する

一方、`EmployeeController` の次の処理は、`HttpSession` も `loginEmployee.role` も確認していない。

- `GET /employeeList`
- `GET /retireeList`
- `POST /restore/{empNo}`
- `POST /physicalDelete/{empNo}`
- `GET /changeInput/{empNo}`
- `POST /changeConfirm`
- `POST /changeEmployee`
- `GET /deleteConfirm/{empNo}`
- `POST /deleteEmployee`

実機でも次を確認した。

1. 未ログインのまま `/retireeList` を直接開くと、退職者管理画面が表示された。
2. 一般ユーザー `10003` で `/employeeList` を直接開くと、全社員一覧が表示された。
3. 一般ユーザー `10003` で `/changeInput/10001` を直接開くと、管理者 `10001` の変更画面が表示された。

修正前の実機証跡: [一般ユーザー_他社員変更画面.png](review-evidence/一般ユーザー_他社員変更画面.png)

**影響:** URLまたはHTTPリクエストを直接送れば、未ログイン者や一般ユーザーが他社員の変更、退職、復元、完全削除を実行できる。

**修正方針:** 「必要に応じてController側で確認」ではなく、「管理操作では必ずController側で確認」に設計を変更する。初心者向けには、共通機能の書き方に合わせた小さな `isAdmin(HttpSession session)` または同等の共通判定に集約し、各管理操作の先頭で使用する方法が理解しやすい。

### [重大] R-02 一般ユーザーが自分または他社員の権限を管理者へ変更できる

`change.html` は利用者の権限に関係なく、`role = 0 / 1` のラジオボタンを表示する。`EmployeeServiceImpl.update()` は画面から送られた `role` をそのまま保存する。

さらにR-01のため、一般ユーザーが他社員の変更画面も直接開ける。本人編集だけに制限したとしても、一般ユーザー本人が自分の `role` を `1` に変更できる。

`input.html` にも管理者権限を選ぶラジオボタンがあり、未ログインまたは一般ユーザーでも社員登録画面を利用できる現仕様では、管理者アカウントを新規作成できる。

**影響:** 権限昇格が可能であり、権限制御機能そのものが成立しない。

**修正方針:** `role` の入力・更新は管理者だけに限定する。一般ユーザーの本人編集では、画面から `role` を送信しないだけでなく、サーバー側でも既存値を維持する。

### [高] R-03 登録できるパスワードとログインできるパスワードの桁数が矛盾する

- `EmployeeForm`: 4文字以上16文字以内で登録・変更可能
- `LoginForm`: 8文字以上でなければログイン処理へ進めない

そのため、4～7文字のパスワードを持つ社員は正常に登録できるが、そのパスワードではログインできない。

**修正方針:** 登録・変更・ログインで同一の桁数規則を使用し、設計書のデータ仕様とテスト観点にも明記する。

### [高] R-04 追加機能の自動テストが存在しない

`EIMS_SpringBoot_Additional/src/test` にテストソースはない。`mvnw.cmd test` は成功するが、出力は `No sources to compile` であり、設計書2.9～5.9のテスト観点は自動検証されていない。

少なくとも次の回帰テストが必要である。

- 未ログイン・一般・管理者のURL直接アクセス
- 一般ユーザーの権限昇格防止
- 4～7文字を含むパスワード規則の整合
- 論理削除、復元、完全削除
- 在籍者だけを対象とする社員番号・氏名・部署検索
- 管理者本人、管理者が他人、一般本人、一般が他人を表示した場合のボタン制御

## 4. 仕様・実装の不一致

### [中] R-05 社員一覧はServiceで在籍者に絞らず、画面で非表示にしている

設計書3.5は、社員一覧でも `deleteFlg = 0` の社員だけを表示するとしている。実装はControllerから `employeeService.findAll()` を呼び、全社員を取得した後、`employee_list.html` の `th:if` で退職者の行だけを非表示にしている。

見た目上は退職者を隠せるが、次の問題がある。

- 取得責務と表示責務が混ざり、初心者が「どこで退職者を除外しているか」を追いにくい。
- 全件が退職者の場合、`employees.empty` は `false` のため、「在籍社員なし」の表示ではなく、行のない表が表示される。

**修正方針:** `findByDeleteFlg(0)` 相当をServiceから呼び、Controllerへ渡す時点で在籍者だけにする。

### [中] R-06 詳細画面の退職状態の文言が設計と異なる

- 設計書5.4: `deleteFlg = 1` は「退職」、`deleteFlg = 0` は「在籍」
- 実画面: 項目名「退職済み」、値「はい／いいえ」

スクリーンショットは実装側の「退職済み／はい・いいえ」と一致するが、本文仕様とは一致しない。教材では本文と画面のどちらを正とするか判断できない。

### [中] R-07 一般ユーザーの許可範囲が設計書内で統一されていない

- 4.1: 一般ユーザーは参照中心で、管理操作は行えない
- 4.4 メニュー表示: 一般ユーザーは「検索、登録などの一般機能」
- 4.4 操作ボタン: 本人編集を許可する場合あり
- 5.4 操作ボタン: 一般ユーザー本人の変更ボタンは表示すると確定的に記載

社員登録、本人編集、パスワード変更、権限変更のどこまでを一般ユーザーへ許可するかを、権限表1か所で確定する必要がある。

### [中] R-08 サーバー側制御が任意表現と必須条件の両方で書かれている

- 4.2、4.5: 「必要に応じて」Controller側でも権限確認
- 4.8、4.9: 直接操作・直接アクセスを防ぐことが完了条件

直接アクセス防止は任意では実現できないため、処理仕様でも必須にする。

## 5. 初心者向けコードとしての評価

### 良い点

- Controller、Service、Repository、Entity、Formの構成は共通機能と同じである。
- 追加機能のためだけの過剰なクラス階層やデザインパターンは増やしていない。
- 論理削除、復元、完全削除は短いメソッドに分けられ、処理の目的を追いやすい。
- 共通レイアウトは `layout.html` に集約されている。

### 改善が必要な点

1. `findByDeleteFlgAndLastNameContainingOrDeleteFlgAndFirstNameContaining` は名前が長く、同じ削除フラグを2回渡す理由も初心者には分かりにくい。
2. `employee_detail.html` の変更・削除ボタン条件は1行が長く、管理者・本人・退職状態の3条件を同時に読ませている。
3. 権限ルールがHTMLにだけ存在し、Controllerに同じルールがないため、「ボタンを隠せば権限制御になる」という誤った理解につながる。
4. `findAll()` の後にHTMLで退職者を除外しており、検索条件の実装場所が統一されていない。
5. `take_additional_screenshots.mjs` はCDP接続、PNGの展開・CRC再計算、DOM加工まで含み、受講者向けコードとしては非常に難しい。教材生成用ツールであることを明記し、受講者が実装するソースとは分離して扱うべきである。

重大な誤字、文字化け、画像リンク切れは確認されなかった。Markdown内の画像参照15件はすべて実ファイルが存在する。

| 現在の表記 | 推奨 | 理由 |

3. R-01を修正後、`AF04_list_general.png` はアクセス拒否または遷移後の画面へ差し替える。
4. 重複している `AF25_after_detail.png` は、意図的な再掲なら同一画像ファイルを参照し、別ファイルとして複製しない。

## 9. 修正優先順位

1. Controller側の認証・権限確認を必須実装する。
2. 一般ユーザーが `role` を更新・登録できないよう、画面とサーバーの両方を修正する。
3. パスワード桁数を登録・変更・ログインで統一する。
4. 権限、論理削除、直接アクセスのテストを追加する。
5. 一般ユーザーに許可する登録・本人編集の範囲を設計書で確定する。
6. 在籍者一覧の絞り込みをService/Repository側へ移す。
7. 退職状態と権限の表示用語を統一する。
8. 加工スクリーンショットと撮影データ条件を明記し、権限修正後に該当画像を再撮影する。

## 10. 初回レビュー時点の判定

デザイン、論理削除、顔写真、ログイン、表示上の権限分岐は実装へ反映されている。しかし、権限機能は「見せない」だけで「実行させない」実装になっておらず、設計書の最重要な完了条件に未達である。

初回レビューでは、**R-01～R-04を解消し、スクリーンショットを再確認するまでは完成扱いにしない**ことを推奨した。対応後の現在仕様については、冒頭の注意書きと `追加機能設計書.md` を参照すること。
